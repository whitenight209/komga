# Komga home reconciler

This is the CD consumer for the **whitenight209/komga** fork. It looks for the newest published, non-draft, non-prerelease `komga-home-<40-hex-commit>` release among the latest 50 releases. The GitHub git ref itself must target that commit. Its two assets are exactly `komga.jar` and `deploy-manifest.json`, containing `schema: 1`, `service: "komga"`, `commit`, and the JAR's `sha256`. An optional, verified rollback-safety attestation consists of `rollback_safe: true` and the exact `previous_commit` checked by CI. This trusts the fork's GitHub release publishers and TLS; review repository access and keep release creation restricted. A checksum and tag do not make an untrusted publisher trusted.

Nothing is configured, installed, or enabled by these examples. In particular, review the VM/user paths and trust and use an independently verified installed JAR hash. The fork includes a custom `scripts/komga.sh` using a versioned JAR; a systemd service may use a different path. Verify your own launch command, JAR path, Java and restart mechanism before setting up CD. A preexisting Java 21 deployment does not demonstrate Java 25 compatibility. Set the config JVM to the exact executable in the service's `ExecStart` and verify release runtime requirements before approving a transition. The preflight checks the configured JVM, not an unrelated shell Java.

1. Set up a local `komga-deploy` account, release reader group, and deployment directory on one filesystem, owned by the deploy account and readable by the unprivileged application account via the group (directory not writable by Komga). Install script and config under administrator-controlled paths. The deploy account needs no SSH, data-directory or secret access. Example file is a template, not a change to your server.
2. With the current service untouched, copy the independently verified, running release JAR to the chosen managed directory as the **regular file** `current.jar`. Compare to the known-good running artifact hash; do not just use a hash discovered by the reconciler as approval. Dry-run first:
   ```sh
   /usr/bin/python3 /usr/local/lib/komga-home/komga-home-deploy.py --config /etc/komga-home-deploy.json adopt --expect-sha256 "$TRUSTED_BASELINE_SHA256"
   ```
   If you also have independent evidence that the installed bytes came from a specific source commit, add `--deployed-commit SHA` to pin the verified source identity for automatic reconciliation. After review, add `--apply` before `adopt` to stage the verified bytes and replace only this managed copy with its managed symlink. The historical JAR path, config and data are untouched; adoption does not restart. Treat changing `ExecStart` to use the new path as a separate planned migration and verify it while running the same baseline. Keep database and application arguments, working directory, service user, and all service environment values intact.
3. Verify the exact `restart_command` and authenticated access controls. The unit example expects a local policy permitting the deploy account to restart **only** `komga.service`; do not give blanket `sudo`. The HTTP health endpoint must be loopback-only in this tool and return HTTP 200 with JSON `{"status":"UP"}` without redirects. Verify its actual path; the example assumes `/ebook/actuator/health`. The deployer does not expose endpoints or weaken Komga auth.
4. Run `reconcile` without `--apply`. By default, apply requires an operator-reviewed transition object in `approved_transitions` with `from_sha256`, `to_commit`, `to_sha256`, and `rollback_compatible: true`. Verify a service data backup and known compatibility of the previous JAR with any schema/data changes made by this candidate. Never approve when older binaries are incompatible; those upgrades need separately managed backups/migration. Approval is intentionally exact and local, never inferred from the incoming manifest. For normal automatic deployments, explicitly set `auto_rollback_safe: true` and an absolute fixed `backup_precheck_command` array. A release is eligible only if CI attests to rollback compatibility from **this exact current deployed source commit** and the local hook exits zero after verifying a fresh, restorable backup. Otherwise no link is changed without the exact manual exception. The same policy must remain enabled while an automatic rollback is pending. The sample intentionally does not create an automatic approval or backup system; choose and test an offline/local hook suited to your data and installation. If a release feed requires authentication, supply short-lived read-only repository access via an administrator-controlled environment; no secrets in this repo or command arguments. HTTP asset requests discard the bearer token on redirects.
5. Timer example is dry-run and runs every 10 minutes from **03:30 KST through 04:50 KST**. Once externally approved, adding `--apply` before `reconcile` permits a new deployment only **03:30–05:00 KST**, with another check before changing the symlink. Missed runs outside the window skip new installation. Recovery of an interrupted transaction is not a new installation and can run outside that window.

The deployer coordinates through a filesystem lock and writes a durable pending journal before atomically switching the JAR link. It performs only the reviewed restart command (no app/data/config replacement), then probes readiness. On failure it records the candidate, restores the previous local hash-verified JAR and restarts/probes again. A killed deploy will follow the same offline path next time, not continue the new deployment. Use the `recover` subcommand with `--apply` for immediate local recovery, without querying GitHub. If rollback is not approved, artifacts or state have changed, or the previous JAR does not become healthy, the deployer stops and leaves the recovery journal in place. Failed commits are not automatically retried, and old artifacts are kept. Do not delete state or jars with a pending transaction. Keep adequate storage and handle reviewed retention separately.

The program emits only bounded operational messages and does not upload logs, application data, or credentials. The configured hooks and filesystem remain trusted local deployment boundaries.
